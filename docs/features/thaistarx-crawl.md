# Краулер thaistarx.com (черновики фан-событий по миру)

Суточная задача `thaistarx-crawl` обходит английскую версию
[thaistarx.com](https://thaistarx.com/en/category/thai-star-events-en/) —
трекер фан-событий тайских артистов по всему миру: фанмиты, концерты,
фанконы, премьеры и финалы серий, фансайны — и кладёт каждое новое
событие **черновиком** в ту же очередь, что и обход афиши
ThaiTicketMajor (см. [ttm-crawl.md](ttm-crawl.md)). Владелец одобряет
или отклоняет каждый; само в афишу ничего не попадает.

Сайт нашла владелец 2026-09-18: «давай спарсим всё, чего не хватает». На
момент разведки на сайте было 125 событий, из них в нашем каталоге не
было **124** — источник закрывает ровно то, чего тайские билетные сайты
не видят: Тайбэй, Макао, Манила, Токио, Сингапур, Хошимин, Сеул,
Лос-Анджелес, Берлин.

## Files

- **`src/lib/thaiStarX.ts`** — чистые парсеры (без БД):
  список (`parseThaiStarXListing`), пост (`parseThaiStarXPost`), даты и
  время из текста (`parseThaiStarXDateText`, `parseThaiStarXTime`,
  `parseUtcOffset`), часовой пояс по месту (`timezoneForPlace`),
  канонизация адреса (`canonicalThaiStarXUrl`), билетный ли хост
  (`isTicketHost`); `scrape*`-обёртки с UA и 15-секундным таймаутом.
- **`src/lib/thaiStarXCrawl.ts`** — краулер `runThaiStarXCrawl`
  (список → новые URL → посты → обогащение с TTM → дедуп → матчинг →
  `EventDraft`), сборка payload `buildThaiStarXPayload`, матчинг состава
  `matchThaiStarXArtists`, сводка `summarizeThaiStarXCrawl`. Режимы:
  `listing: "recent"` (суточная задача) и `"archive"` (разовая кнопка);
  `apply: false` — сухой прогон с планом.
- **`src/lib/performerMatching.ts`** — `loadTagCatalog` +
  `matchTagsAgainstCatalog`: матчинг ТЕГОВ поста по каталогу (см. ниже).
- **`src/lib/scheduledJobs.ts`** — задача `thaistarx-crawl` (`logKind`
  тот же, `logsItems: true`, раз в сутки).
- **`src/app/admin/(protected)/imports/thaiStarXActions.ts`** — экшен
  `startThaiStarXArchiveCrawl`: разовый обход архива фоном (одна
  карточка в журнале, «Остановить» там же; второй параллельный не
  запускается).
- **`src/app/admin/(protected)/imports/page.tsx`** — карточка «ThaiStarX:
  фан-события по миру» с кнопкой архива и ссылкой на задачу; очередь
  черновиков общая с TTM, в строке черновика виден хост источника и
  часовой пояс (если не Бангкок).
- **`src/app/admin/(protected)/imports/ttm-poster/route.ts`** — прокси
  постера принимает и `thaistarx.com`.
- **`src/app/admin/(protected)/events/importActions.ts`** и
  **`imports/eventDraftsBatch.ts`** — одобрение понимает черновики без
  времени и с часовым поясом (см. «Одобрение»).

## Что на сайте и что берём

WordPress (тема CoverNews), REST API закрыт — разбираем HTML; всё в
обычной разметке, JS не нужен. Разведка 2026-09-18.

**Список** `/en/category/thai-star-events-en/` (+ `page/N/`) — все
события разом, новые сверху, по 10 `<article>` на странице, на
2026-09-18 — 13 страниц. Отдельный список «предстоящие»
(`coming-soon-en`) есть, но им почти не пользуются (1 запись из 125),
поэтому суточный обход листает общий список с первой страницы и
**останавливается на первой странице, где все посты уже знакомы**
(потолок 3 страницы); архив листает до конца (потолок 30).

Самое ценное в списке — CSS-классы `<article>`: тема кладёт туда теги и
рубрики поста. Тег `tag-20260404-en` — **дата события** (у многодневных
по тегу на день), остальные теги — слаги артистов, пейрингов и
агентств (`forcebook`, `namtan-tipnaree`, `lykn`, `gmmtv`). Даты из
тегов надёжнее строки «Date:» в тексте — ту пишут руками в десятке
форматов, а при переносе события в тегах стоит **новая** дата
(«New Date: March 14, 2026 → Original Date: September 13, 2025»).

**Пост** `/en/<слаг>/` → черновик:

| На сайте | Куда |
| --- | --- |
| `h1.entry-title` | `title` |
| теги-даты статьи (запас — текст «Date:», `parseThaiStarXDateText`) | `date` + `extraDates`; без даты черновик не заводится, адрес не запоминается — перечитается назавтра |
| «Time: 6:30 PM (UTC+9)» / «18:00 (UTC+8)» (есть у половины постов) | `startTime` по МЕСТНОМУ времени площадки; нет — событие без времени |
| «Venue: Toyosu PIT, Tokyo, Japan» (+ строка-продолжение без метки, кроме примечаний про стрим) | `venue` |
| страна/город из «Venue:», затем из названия поста («… in Taipei 2026»), затем смещение «(UTC+8)» | `timezone` (IANA) — при одобрении `Event.timezone`; на 124 из 125 постов распознаётся |
| вступительные абзацы (от первого h2 до «📅 Event Information») | `description` |
| первая иллюстрация поста, полноразмерная из `srcset` (запас — `og:image`) | `posterUrl` — в очереди через прокси, к нам скачивается при одобрении как `/uploads/posters/thaistarx-<слаг>.webp` (своё имя: у картинок сайта имена бывают общими, а помощник считает «уже на диске» по имени) |
| «Ticket Sales Open:» / «General Ticket Sales Begin:» — общая продажа важнее членского пресейла | `presaleDate` + `presaleTime` |
| ссылки блока «🎫 Ticket Information» (ссылки из строки «Ticketing Platform(s)» первыми; соцсети и «official website» отсеиваются, имена платформ из текста — без дат) | `thaiStarX.ticketLinks`; `presaleUrl` = TTM, иначе первая билетная ссылка — при одобрении `Event.presaleUrl` («где купить»), даже без даты старта продаж; нет билетной ссылки — пусто, сам пост билетами не торгует |
| ссылка блока «📣 Official Announcement» | `thaiStarX.announcementUrl` |
| рубрики (fan-meeting, thai-star-concert, fancon, premiere-event, finale-event, fansign-event, mid-series-screening) | `thaiStarX.categories` — пока только в payload |

Payload черновика — в форме `TtmEvent` (её понимают очередь, одобрение и
прокси постера) плюс `presaleUrl`, `timezone` и блок `thaiStarX`
(`ThaiStarXDraftPayload`).

## Обогащение с ThaiTicketMajor

Просьба владельца: «если есть ThaiTicketMajor, у нас для него уже парсер
есть». У 30 из 125 постов в блоке билетов есть ссылка на TTM — тогда
страница TTM дочитывается существующим `scrapeTtmEvent`, и из неё
берутся **время, цены и строка «Artists»** (в посте времени часто нет,
цен не бывает никогда). Название, даты, описание, постер и площадка —
поста; постер с TTM — только если у поста своего нет.

Память по TTM-адресу, чтобы не плодить второй черновик того же события:

- событие с этим `sourceUrl` уже в каталоге (или черновик TTM
  APPROVED с `eventId`) — наш адрес запоминается черновиком APPROVED с
  тем же `eventId`, как «Одобрить» при существующем событии;
- черновик TTM REJECTED — владелец уже отказалась, наш тоже REJECTED;
- черновик TTM PENDING — свой не плодим, запоминаем NO_MATCH: через
  неделю на перепроверке тот уже разобран.

## Состав: матчинг тегов (`matchTagsAgainstCatalog`)

Состав события в прозе поста ненадёжен («Presented by … Force
Jiratchapong Srisang and Book …»), а теги проставляет редакция — по ним
и матчим, каталог грузится **один раз на прогон** (сравнение без
дефисов в SQL не выразить). Правила, для каждого тега (даты
отбрасываются):

1. **Пейринг**: слаг равен склейке ников участников в любом порядке
   («williamest» = William + Est, `Pairing.name` в каталоге пуст) —
   привязываются оба.
2. **Исполнитель целиком**: слаг равен нику или `musicAlias` без
   дефисов/точек/регистра («jasp-er» = JASP.ER, «lykn» = LYKN).
3. **«ник-имя»** («namtan-tipnaree»): первая часть — ник, остальное —
   подсказка к реальному имени. Кандидаты по нику; несколько — разводим
   по началу `realName`. Ровно один — привязка, иначе тёзки в
   `ambiguousArtists` (жёлтый чип в очереди, как у TTM).
4. Ничего не сработало — тег в `unmatched` (так уходят агентства:
   «gmmtv», «ch3-thailand»).

Плюс строка «Artists» с TTM, если было обогащение, — через общий
`matchArtistsByNickname`. Привязки объединяются по `performerId`, тёзки
— по нику; артист, уже привязанный по тегу, из тёзок выпадает.
Никакого фаззи: ложная привязка хуже пропуска.

## Прогон задачи

1. Память — до списка: `Event.sourceUrl` с `thaistarx.com` (навсегда
   пропуск), черновики по адресу (PENDING/APPROVED/REJECTED — пропуск,
   NO_MATCH старше 7 дней — перепроверка).
2. Список: суточный — до первой страницы без новых, архив — до конца.
3. Посты с паузой 1,7 с (потолок за прогон: 40 свежих / 250 архивных).
   Обогащение с TTM — ещё одна страница с той же паузой.
4. Дедуп по содержимому (`findCatalogDuplicate`): сильное совпадение —
   черновика нет, `sourceUrl` бэкфилится, адрес запоминается APPROVED;
   слабое — пометка `possibleDuplicateOf`.
5. Матчинг → PENDING (с `ImportedItem` типа `event-draft`) или NO_MATCH.
6. Появились PENDING — одно `notifyAdmins("import", …)` на прогон.

Сводка — `summarizeThaiStarXCrawl` (страниц списка / постов / скачано /
черновиков + ники / без совпадений / уже в каталоге / пропущено /
дочитано с TTM). Сухой прогон (`apply: false`) возвращает `plan` —
по строке на пост со статусом и привязками.

**Архив** — кнопкой «Обойти архив (все прошедшие)» на `/admin/imports`
(вкладка «События»), фоном через `logImportRun` (kind `thaistarx-crawl`,
«Остановить» в журнале), второй параллельный не стартует. Не скриптом
с локальной машины: база на проде.

## Одобрение

Тот же путь, что у TTM (`createEventFromTtmImport` через
`ttmDraftSubmission`), с двумя расширениями, нужными этому источнику:

- **Событие без времени.** У половины постов только дата; раньше
  одобрение требовало время начала. Теперь пустое время → `startsAt`
  00:00 и `hasTime: false` — как у пустого времени в ручной форме
  события и у фестивалей musicfestival.in.th. Обязательны название,
  место, дата.
- **Часовой пояс.** `TtmImportSubmission.timezone` → `Event.timezone`:
  фанмит в Тайбэе показывается по тайбэйскому времени, а не как
  «тайское время».
- **Ссылка на продажи.** `payload.presaleUrl` → `Event.presaleUrl` даже
  без даты старта продаж; у черновиков TTM поведение прежнее (ссылка на
  саму страницу TTM при известной дате).
