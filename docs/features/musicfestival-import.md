# Краулер фестивалей musicfestival.in.th

Суточная задача `musicfestival-crawl` открывает список будущих фестивалей
на [musicfestival.in.th/en/festivals](https://www.musicfestival.in.th/en/festivals)
и **сразу заводит события** по новым адресам — без очереди черновиков
(просьба владельца: «создаём и сохраняем на сайте»). Прошедшие
фестивали ([/en/past-festivals](https://www.musicfestival.in.th/en/past-festivals))
заведены разово скриптом. Лайнап берётся **целиком**: артисты из каталога
привязываются, остальные заводятся **заготовками** (`Performer.stub`) —
их список владелец дополняет руками.

Главное правило владельца: **уже известные адреса не перечитываются** —
обходятся только новые. Ничего не обновляется задним числом.

## Files

- **`src/lib/musicFestival.ts`** — чистые парсеры HTML (без БД, как
  `thaiticketmajor.ts`): список (`parseMusicFestivalListing`), страница
  фестиваля (`parseMusicFestivalPage`), страница артиста
  (`parseMusicFestivalArtist`), сетка расписания
  (`parseMusicFestivalShowtime`), даты (`parseMusicFestivalDates`),
  канонизация адресов (`canonicalMusicFestivalUrl`,
  `canonicalMusicFestivalArtistUrl`), `scrape*`-обёртки с UA и
  15-секундным таймаутом.
- **`src/lib/musicFestivalCrawl.ts`** — краулер `runMusicFestivalCrawl`
  (список → новые URL → страницы → матчинг лайнапа → `Event` +
  заготовки), импорт одного адреса `importMusicFestivalByUrl`,
  дозаполнение уже заведённых `refreshMusicFestivalEvents` и сводка
  `summarizeMusicFestivalCrawl`. Один код на
  суточную задачу (`listing: "upcoming"`) и разовый скрипт
  (`listing: "past"`); `apply: false` — сухой прогон с планом.
- **`src/lib/performerMatching.ts`** — `matchFestivalArtists`: матчинг
  лайнапа (см. ниже).
- **`src/lib/localImage.ts`** — у `downloadRemoteImage` появился
  `opts.localBase`: своё имя локального файла. Нужно потому, что постер
  каждого фестиваля на сайте лежит как `…/<слаг>/thumbnail.jpg` (или
  `cover.jpg`), а помощник проверяет «уже на диске» по имени файла — без
  своего имени второй фестиваль получил бы постер первого. В allowlist
  скачивания добавлен `image/avif` (часть фото и постеров сайт отдаёт в
  AVIF; sharp читает, на диск ложится WebP; ручной `/api/upload` не
  тронут).
- **`src/lib/scheduledJobs.ts`** — задача `musicfestival-crawl`
  (`logKind: "musicfestival-crawl"`, `logsItems: true`, раз в сутки,
  `supportsTargets: false`).
- **`scripts/import-musicfestival-past.ts`** — разовый импорт
  прошедших.
- **`scripts/refresh-musicfestival-events.ts`** — разовое дозаполнение
  уже заведённых событий (см. ниже).
- Админка: фильтр «Заготовки парсеров (без данных)» на
  `/admin/performers` (`catalogFilters.ts`, флаг `?stub=1`), плитка
  «заготовок исполнителей с фестивалей» на дашборде, строка задачи в
  списке «Обходы по расписанию» (кнопка «Заготовки исполнителей: N») и
  карточка «Фестиваль по ссылке» на вкладке «События» в `/admin/imports`,
  вкладка «Фестивали» в `/admin/schedule`.

## Что на сайте и что берём

Сайт — React Router с серверным рендером: всё лежит в обычной разметке,
JS не нужен; `robots.txt` разрешает обход. Разведка 2026-09-05.

**Списки** `/en/festivals` и `/en/past-festivals` — по 12 карточек
(`<a href="/en/festivals/<слаг>">` с `<h3>`), дальше тот же адрес с
`?offset=12`, `?offset=24`…; флаг «есть ещё» лежит в loader-данных React
Router прямо в HTML (`"hasMore",true`) — парсер читает его оттуда, а при
отсутствии считает страницу последней, когда карточек меньше 12. Краулер
листает до `hasMore=false` (потолок 30 страниц), пауза между страницами
списка 1.2 с. На 2026-09-05: будущих 37, прошедших 23 (в sitemap тех же
59 фестивалей — отдельного источника не нужно).

**Страница фестиваля** `/en/festivals/<слаг>` → `Event`:

| На сайте | Куда |
| --- | --- |
| `h1` (запас — `og:title` без « \| musicfestival.in.th») | `title` |
| дата текстом: «16 October 2026», «12–13 December 2026», «31 October – 2 November 2026» | `EventOccurrence` на **каждый день** диапазона (развёрнут целиком, потолок 14 дней), `hasTime=false` — времени сайт не даёт; без разобранной даты событие не заводится, адрес не запоминается — перечитается назавтра |
| описание: один `<p>` с переносами либо HTML-блок абзацев/списков | `description` — только текст со страницы (`<br>` → перенос, абзацы через пустую строку) |
| чипы жанров (ссылки `/genre/…`; чип «Edition: 2026» — не жанр) | `tags` — чипами на странице события, как жанры сериала |
| Venue: название (ссылка `/venues/…`), город, ссылка на Google Maps | `venue` = «Название, Город», `address` = город/район отдельно, `mapsUrl` = ссылка на карту (площадка на витрине становится ссылкой); `locationId` — только при точном совпадении названия с каталожной `Location` |

| Lineup: карточки-ссылки `/en/artists/<слаг>` с фото и именем, счётчик «N artists» | состав события целиком (см. ниже); счётчик сверяется с числом снятых карточек, расхождение — предупреждение в лог |
| «DAY 1» / «18:00-19:00» на карточках у фестивалей с расписанием (есть и ссылка «See showtime») | у многодневных — `OccurrenceLineup` дня (публично «Лайнап по дням»); карточки без дня остаются в общем составе |
| страница расписания `/en/showtime/<слаг>` | `OccurrenceLineup.timeText` и `.stage` у участника дня (см. ниже) |
| Organizer | `organizer` — отдельным полем на странице события |
| секция «Showtime» — галерея афиш расписания картинками (`…/<слаг>/showtime/…`) | `showtimeImages` → первые три ложатся в фотоблок события (`EventPhoto`), файлами `musicfestival-<слаг>-showtime-N.webp` |
| тайская версия `/th/…` | не берётся: у Event нет поля для тайского названия |

**Страница артиста** `/en/artists/<слаг>`: имя, фото, жанры и списки
«Upcoming/Past Shows» — соцсетей и биографии там **нет**. Фото — тот же
файл `/media/artists/<слаг>.jpg`, что и на карточке лайнапа, поэтому
краулер страницы артистов **не открывает** (меньше запросов); парсер
`parseMusicFestivalArtist` есть на будущее и покрыт тестом.

**Галерея Showtime** (`showtimeImages`) — картинки-афиши расписания,
которые у части фестивалей выложены отдельной секцией. Отбор идёт по
двум независимым признакам, совпало любое: секция, у которой `h2` —
«Showtime», и путь картинки `/media/festivals/<слаг>/showtime/…`. Одного
признака мало: заголовок секции сайт может переименовать или перевести, а
имена файлов внутри папки произвольные («showtime-1.jpg» у Monster,
«rock-showtime-update.jpeg» у GFest) — цепляться за них нельзя. Важно
именно не перепутать: рядом на той же странице лежат обложка
`/cover.jpg`, логотип шапки, `/highlight.jpg`, соседняя секция «Gallery»,
галерея прошлых лет `/previous/…` и десятки фото артистов
`/media/artists/…` — ничего из этого в поле не попадает. Галереи нет —
пустой массив.

**Страница расписания** `/en/showtime/<слаг>` (её адрес отдаёт
`showtimeUrl`) — `parseMusicFestivalShowtime` → `MusicFestivalShowtime`:
`dayLabels` («25 Jul», «26 Jul») и `slots` — по выходу на сцену
(`dayLabel`, `dayIndex` 0-based, `stage`, `artistName`, `artistUrl`
канонический, `timeText` «16:00-16:45» или null). Разметка — не таблица, а
три ряда абсолютно спозиционированных колонок с инлайновыми стилями: ряд
подписей дней, ряд названий сцен и грид, где в колонке-сцене лежат
карточки-ссылки на артистов; у всех трёх рядов первая ячейка — линейка
времени слева. Колонка связывается со сценой и днём **по структуре и
арифметике вёрстки**, а не по глобальному порядку блоков в документе
(любой лишний блок той же ширины — второй, мобильный вариант шапки —
сдвинул бы всё): колонка — прямой родитель карточки, ряд колонок — их
общий родитель, ширина колонки берётся со страницы и по ней добираются
пустые колонки (сцена, где в этот день никто не играет); ряд сцен — группа
блоков той же ширины вне грида, где ячеек ровно столько же, сколько
колонок; ряд дней — группа, где ширина каждой ячейки кратна ширине
колонки, а сумма равна ширине грида, и ширина подписи дня равна числу его
сцен (600 = 4 × 150) — поэтому раскладка переживёт фестиваль с разным
числом сцен по дням. Ничего не достраивается: колонка без сцены или без
дня — слот **не возвращается** (лучше меньше, чем не в тот день),
карточка без времени — `timeText: null`. У Monster 2026 — 66 слотов,
поровну на два дня.

**Расписание → дни события.** Слоты раскладываются по `EventOccurrence`
в порядке дат фестиваля (`dayIndex` совпадает с номером дня), артист
берётся тем же матчингом, что и лайнап. Расписание **главнее** пометок
«DAY N» на карточках лайнапа: у него есть и время, и сцена, а пометка
даёт только день. Кого расписание не назвало, того по-прежнему разносит
пометка «DAY N» — с пустыми временем и сценой. Артист, попавший в
несколько слотов одного дня, остаётся в дне один раз (ключ
`OccurrenceLineup` — пара «день + исполнитель»): вторым выходом
пришлось бы жертвовать, и остаётся первый по странице. Живой прогон
Monster 2026: 33 участника в каждом из двух дней, у 31 из них время, у
всех — одна из четырёх сцен.

## Лайнап: матчинг и заготовки

`matchFestivalArtists` (`performerMatching.ts`), для каждого артиста:

1. по **адресу источника** — `Performer.musicFestivalUrl` равен адресу
   его страницы (заготовки прошлых прогонов и записи, где владелец
   поставил ссылку сам): так один и тот же артист второго фестиваля не
   заводится дважды;
2. по **имени** — точное case-insensitive совпадение с `name` или
   `musicAlias` у SOLO/BAND (маскоты не выступают). Ровно один кандидат
   — привязка; **несколько тёзок — привязки нет** («New», «Earth»,
   «Ploy» в каталоге по нескольку), артист заводится заготовкой: ложная
   привязка хуже дубля — дубль виден в списке заготовок и сливается через
   «Дубли», а слияние переносит `musicFestivalUrl` на выжившего.

Никакого фаззи, как и везде в матчинге.

**Заготовка** — `Performer` с `name` (как на сайте, бывает тайское — тогда
слага нет), **`type: BAND`** (правка владельца 2026-09-10: сайт группы от
сольных не отличает, но это МУЗЫКАЛЬНЫЙ фестиваль — в лайнапе преобладают
группы, а прежний SOLO по умолчанию отправлял их все в «Актёров»:
«много копий групп в артистах». Сольные исполнители правятся руками там
же, где дописывается всё остальное; константа `FESTIVAL_STUB_TYPE` в
`musicFestivalCrawl.ts`. Заготовки, заведённые ДО правки, не трогали —
их разбирают по мере заполнения), `photoUrl` (скачано к нам как
`/uploads/performers/musicfestival-<слаг>.webp`, если фото на сайте было),
`musicFestivalUrl` (`@unique`) и **`stub: true`**. Жанры артиста никуда не
пишутся — поля нет.

**Список заготовок** — `/admin/performers?stub=1` (флаг «Заготовки
парсеров (без данных)» в панели фильтров): над списком подсказка, что
это и как отсюда выпадает; клик по строке — обычная правка. Ссылки на
список: плитка «заготовок исполнителей с фестивалей» в «Требует
внимания» на дашборде и карточка «Фестивали musicfestival.in.th» на
вкладке «События» в импортах (там же счётчик). В бейдж сайдбара
`/admin/imports` заготовки **не входят**: их сотни после импорта
прошедших, и постоянное число утопило бы остальные очереди.

**Когда заготовка перестаёт быть заготовкой**: при сохранении профиля в
форме исполнителя (`updatePerformer`, scope «general») флаг снимается —
владелец открыл, посмотрел/дополнил и сохранил. Именно факт сохранения,
а не полнота полей: у группы может не быть ни даты рождения, ни био, и
проверка «заполнено ли» гадала бы. Ссылка на источник показывается в
форме строкой «Источник записи — страница артиста на musicfestival.in.th»
(руками не правится) и на публичной странице артиста в «Источниках».

## Один фестиваль по ссылке

`importMusicFestivalByUrl(url)` — разовый импорт одного адреса, не
дожидаясь суточной задачи (просьба владельца 2026-09-06). На
`/admin/imports` это поле «Фестиваль по ссылке» в карточке «Фестивали
musicfestival.in.th» (`MusicFestivalUrlImport.tsx` → серверное действие
`importMusicFestivalEvent`). Делает ровно то же, что обход: страница,
лайнап, расписание по сценам, афиши, заготовки исполнителей — экрана
проверки нет намеренно, у источника правило «создаём и сохраняем сразу».

Осторожнее обхода в двух местах: событие по этому адресу уже есть —
возвращаем его (`status: "exists"`), ничего не трогая; фестиваль похож
на событие из каталога — тоже не создаём (`status: "duplicate"`), а
показываем, на что похож, решает владелец. Пометок в памяти обхода
ручной прогон не оставляет.

Поле «Событие по ссылке» (билетные сайты) ссылку на musicfestival.in.th
не берёт — у неё свой импорт, и вместо «не узнаю сайт» оно теперь
подсказывает, в какой карточке импортировать (жалоба владельца
2026-09-06).

## Дозаполнение уже заведённых событий

`scripts/refresh-musicfestival-events.ts` (логика —
`refreshMusicFestivalEvents`) читает страницы событий, которые у нас УЖЕ
есть, и дозаполняет то, чего у них нет: организатора, адрес, ссылку на
карту, теги, афиши расписания и состав по дням со временем и сценами.
Нужен потому, что обход по правилу владельца не перечитывает знакомые
адреса, а поля и расписание появились позже самих событий.

Главное правило прогона — **только дозаполняет**: заполненное поле не
перезаписывается, фотоблок не трогается, если в нём уже что-то есть, а у
строки состава проставляются лишь ПУСТЫЕ время и сцена. Удалять он не
умеет вовсе, поэтому перезапуск безопасен — второй раз просто нечего
делать. Дни события сопоставляются с датами фестиваля по самой дате (а
не по порядку): день, которого на сайте нет, остаётся как есть. Артист
из расписания, которого не было в общем составе события, добавляется и
туда; неизвестный каталогу — заводится заготовкой, как при обходе.

Состав по дням заводится там, где день отличается от события:
многодневный фестиваль либо однодневный, но с расписанием по сценам —
тогда день добавляет время и сцену, а не повторяет состав.

```
npx tsx scripts/refresh-musicfestival-events.ts             # план
npx tsx scripts/refresh-musicfestival-events.ts --limit 3   # план по трём
npx tsx scripts/refresh-musicfestival-events.ts --apply     # применить
```

На проде:

```
docker compose exec app npx tsx scripts/refresh-musicfestival-events.ts --apply
```

## Дедуп событий

- **По адресу**: `Event.sourceUrl` (канонический адрес фестиваля) — и
  созданные краулером, и заведённые руками с этой ссылкой; плюс
  `EventDraft.sourceUrl` с этим адресом (см. следующий пункт). Такие
  адреса из списка **не перечитываются вовсе**.
- **По содержимому**: перед созданием `findCatalogDuplicate`
  (`eventDedupe.ts`, тот же матчинг, что у обхода афиши TTM). Сильное
  совпадение (название + даты) — фестиваль уже есть в каталоге под
  другим адресом (например, из TTM): второе событие **не создаётся**,
  `sourceUrl` бэкфилится, если был пуст, а адрес запоминается
  `EventDraft` со статусом APPROVED и `eventId` — ровно так обход афиши
  закрывает свои дубли; в очередь на `/admin/imports` такие не попадают
  (там только PENDING). Состав существующего события не трогается.
  Слабое совпадение — событие создаётся, в сводке «возможных дублей N».

## Прогон задачи

1. Список будущих целиком (все страницы `?offset=`).
2. Известные адреса отсеиваются; новые — до **20 фестивалей за прогон**
   (первый прогон добирает хвост в следующие дни), с паузой **1.7 с**
   между страницами фестивалей. Кнопка «Остановить» работает между
   страницами (`checkImportCancelled`).
3. По каждой странице: дедуп → матчинг → постер и фото заготовок
   скачиваются **до** транзакции → одна транзакция: заготовки + событие
   со всем составом (и лайнапами дней). Ошибка одной страницы прогон не
   роняет.
4. История правок (`logAudit`, автор «система»): CREATE события с
   `note: импорт фестиваля: <url>` и CREATE каждой заготовки с `note:
   заготовка из лайнапа фестиваля: <url артиста>`. В журнал прогона —
   `ImportedItem` на событие (`event`) и на каждую заготовку
   (`performer`, подпись «(заготовка)») — видны на вкладке задачи в
   `/admin/schedule` и в «Последнем спарсенном».
5. Появились события → **одно** `notifyAdmins("import", "Фестивали
   musicfestival.in.th: событий +N, заготовок исполнителей +M")` со
   ссылкой на список заготовок.

Сводка (`summarizeMusicFestivalCrawl`): «будущие: карточек 37, скачано
страниц 3, событий +3 (…), артистов привязано 9, заготовок +16 (тёзок
1), знакомых пропущено 2».

## Разовый импорт прошедших

`scripts/import-musicfestival-past.ts` — тот же краулер по
`/en/past-festivals`. Без флагов — сухой прогон: печатает план по каждому
фестивалю (даты, площадка, кто совпал, кого заведёт, тёзки, «похоже на
…»), ничего не пишет и картинки не качает. `--limit N` — только первые N
новых. `--apply` — заводит; прогон пишется в журнал импортов тем же kind
`musicfestival-crawl`. Известные адреса пропускаются — перезапуск
безопасен.

```
npx tsx scripts/import-musicfestival-past.ts                 # план
npx tsx scripts/import-musicfestival-past.ts --limit 3       # план по трём
npx tsx scripts/import-musicfestival-past.ts --apply         # завести все
```

На проде:

```
docker compose exec app npx tsx scripts/import-musicfestival-past.ts --apply
```

Прошедшие они только по датам — афиша сама раскладывает их в архив.
После импорта ожидается несколько сотен заготовок (у больших фестивалей
по 50+ артистов) — их и показывает список заготовок.
