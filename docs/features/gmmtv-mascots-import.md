# Краулер маскотов GMMTV (черновики маскотов)

Недельная задача `gmmtv-mascots` проверяет страницу
[Mascots](https://gmmtv.fandom.com/wiki/Mascots) фан-вики GMMTV и ищет
маскотов, которых ещё нет в каталоге. Найденное становится
**черновиком** в очереди на проверку (вкладка «Маскоты» в
`/admin/imports`); владелец одобряет или отклоняет каждый — само в
каталог ничего не попадает (та же архитектура «краулер → черновики →
одобрение», что у краулера афиши TTM, см. [ttm-crawl.md](ttm-crawl.md)).

Маскоты бывают не только у GMMTV, но расписание пока ходит только по
этой странице — у неё стабильная структура и есть дешёвый признак
изменений (ревизия).

Fandom — это MediaWiki: ходим через **официальный `api.php`**
(`action=query` за ревизией, `action=parse` за HTML), как остальные
вики-импортёры (`mediawikiParse.ts`), а не скрейпингом страницы.

## Files

- **`src/lib/gmmtvMascots.ts`** — парсер страницы
  (`parseGmmtvMascots`, чистый), проверка ревизии
  (`fetchGmmtvMascotsRevision`), сам краулер (`runGmmtvMascotsCrawl` +
  `summarizeGmmtvMascots`) и нормализация имени (`normalizeMascotName`).
- **`src/lib/performerMatching.ts`** — `matchMascotOwners`: матчинг
  владельцев с каталогом (рядом с `matchArtistsByNickname` от TTM, но
  своя функция — см. «Матчинг владельцев»).
- **`src/lib/scheduledJobs.ts`** — задача `gmmtv-mascots` в
  `JOB_DEFINITIONS` (`logKind: "gmmtv-mascots"`, `logsItems: true`,
  `intervalDays: 7` — см. «Недельный интервал»).
- **`src/app/admin/(protected)/imports/`** — очередь на вкладке
  «Маскоты» (`page.tsx`), экшены «Одобрить»/«Отклонить»
  (`mascotDraftActions.ts`).

## Дешёвая проверка изменений: ревизия страницы

Поле «Last edit» на вики — это последняя **ревизия** страницы. Перед
парсингом прогон берёт её официальным
`action=query&prop=revisions&rvprop=ids|timestamp` (один лёгкий запрос
без текста) и сравнивает с последней обработанной, которая хранится
строкой в `SiteSetting` под ключом `gmmtv_mascots_last_revid`
(константа `GMMTV_MASCOTS_REVISION_SETTING`; своя таблица-состояние не
нужна — состояние здесь одно число, а служебные ключи на
`/admin/settings` не показываются). Ревизия та же → прогон
заканчивается мгновенно со сводкой «изменений нет», страница не
скачивается и не парсится.

Ревизия запоминается **после** успешной обработки: упавший на середине
прогон не «съедает» изменение. Распарс в ноль секций при живой странице
— падение (сменилась разметка), ревизия тоже не обновляется.

## Структура страницы и парсер

Страница Mascots — не одна общая таблица, а **секция на маскота**:
плоский `<h2><span class="mw-headline" id="Якорь">Имя</span></h2>` (без
обёртки `mw-heading` — `contentAfterHeading` из `mediawikiParse.ts`
различает обе формы сам), сразу за ним `<table class="fandom-table">` из
трёх колонок Image / Description / Accounts и, у части маскотов,
строкой «Live debut: …». Секция References маскотом не считается.

Из секции берётся:

- **имя** — текст заголовка; **ссылка** — `…/wiki/Mascots#Якорь`
  (своей страницы у маскота на вики нет);
- **картинка** — первый `<img>` первой ячейки со
  `static.wikia.nocookie.net` (настоящий адрес лежит в `data-src` —
  картинки lazyload; у секций со слайдшоу, как у Flarey, — то же самое
  внутри слайда); хвост `scale-to-width-down/150` отрезается, остаётся
  полноразмерная;
- **описание** — текст ячейки Description без сносок-цифр;
- **владельцы** — из устойчивой формулировки описания: «X is/was the
  mascot of the [former] boys/girls love pair `<a>Tay</a>`-`<a>New</a>` /
  boy group `<a>LYKN</a>` / actor `<a>Sky</a>`, born …». Берётся кусок
  между «mascot of the» и первой запятой, в нём — ссылки `/wiki/…`:
  текст ссылки — ник, `title` — полный заголовок страницы владельца
  («Tay Tawan Vihokratana» — ник + настоящее имя, по нему матчинг
  разводит тёзок). Ссылок нет (вживую: «boy group JASP.ER») — берётся
  голый текст, причём пара без ссылок разбирается на двоих по
  «-»/«&»/« and », а не-пара — нет (в имени группы дефис и точка
  легальны).

## `MascotDraft` — своя таблица, дедуп по имени

Как `EventDraft`: до одобрения краулер публичной таблицы `Performer` не
касается вовсе, таблица заодно и память краулера (REJECTED повторный
обход не воскрешает, PENDING не перекачивается — он и так ждёт).

Ключ дедупа — **нормализованное имя** (`nameKey` `@unique`:
NFKC + casefold + схлопнутые пробелы), а не `sourceUrl`: у маскота нет
своей страницы на вики — только якорь-секция общей, и якорь — производная
того же имени; а дедуп против каталога (маскоты, заведённые руками, у
которых никакого sourceUrl нет) всё равно возможен только по имени —
одна нормализация обслуживает оба сравнения.

Поля: `nameKey` (ключ), `name` (как на вики), `sourceUrl` (ссылка на
секцию), `payload Json` (весь распарс `GmmtvMascot` + `unmatchedOwners`
— несовпавшие имена владельцев), `matchedOwners Json`
(`[{performerId, name, type}]` — Json, а не join-таблица: нужны только
чипы в очереди и привязка при одобрении), `status`
(PENDING/APPROVED/REJECTED), `performerId?` (после одобрения),
`createdAt`/`reviewedAt`.

## Матчинг владельцев

`matchMascotOwners` (`performerMatching.ts`) — не
`matchArtistsByNickname`: владельцем бывает и **группа** (BAND по
`name` — правка владельца 2026-09-05, см. `searchMascotOwnerOptions`),
а ник сольника в каталоге не уникален («New», «Earth», «Win» — по 4–7
тёзок), и правило «последний в Map выигрывает» привязало бы маскота к
чужому человеку.

Правила: точное case-insensitive совпадение по
`name`/`realName`/`musicAlias` у SOLO и по `name` у BAND; подсказка из
формулировки («pair»/«actor» → SOLO, «group» → BAND) отсекает тёзок
другого типа; несколько тёзок разводятся настоящим именем из заголовка
вики-страницы («New Thitipoom Techa-apaikhun» → realName «Thitipoom
Techa-apaikhun»). Не развелись — имя уходит в несовпавшие (серым в
карточке очереди): ложная привязка хуже пропуска, как и везде в
матчинге. Пейринги (Pairing) не матчатся — только люди и группы.

## Недельный интервал расписания

У планировщика не было ничего, кроме «час + ежедневно». Минимальная
недельность — поле `intervalDays?` в `JobDefinition` (в код, не в БД:
день недели не выбирается, неделя отсчитывается от последнего прогона):
`isDue` пускает задачу, когда наступил её час **и** с `lastRunAt`
прошло ≥ `intervalDays` календарных дней. Дефолт 1 — прежнее «сегодня
ещё не запускались», существующие задачи не изменились. `isDue`
экспортирована ради юнит-теста.

## Прогон задачи

1. Проверка ревизии (см. выше); не менялась — конец.
2. `action=parse` → `parseGmmtvMascots`.
3. Дедуп: маскот с таким нормализованным именем уже есть в каталоге
   (`Performer` type MASCOT, включая заведённых руками) — пропуск;
   черновик с таким `nameKey` уже существует (любой статус) — пропуск.
4. Новым — матчинг владельцев → `MascotDraft` PENDING (+ `ImportedItem`
   типа `mascot-draft` в журнал: история задачи на вкладке расписания).
5. Ревизия запоминается; появились новые PENDING → **одно**
   `notifyAdmins("import", "Черновики маскотов: +N…")` с dedupKey
   прогона.

Прогон пишется через `logImportRun` (kind `gmmtv-mascots`), сводка —
`summarizeGmmtvMascots` (на странице / в каталоге / черновиков + чьи
владельцы совпали / кого не нашли / ревизия).

## Очередь в админке

`/admin/imports?tab=mascots`, блок «Черновики маскотов (N)». Карточка:
картинка-превью (прямой хотлинк со `static.wikia.nocookie.net` —
фандомный CDN, в отличие от Akamai у TTM, отдаёт картинки кросс-сайтово,
прокси не нужен; в базу чужой хост не пишется), имя ссылкой на секцию
вики, описание, чипы совпавших владельцев (ссылки на их
админ-карточки), серым — «не нашли: …».

- **«Одобрить»** — создаёт `Performer` типа MASCOT: картинка
  скачивается к нам (`downloadRemoteImage`, папка `performers`),
  описание — в `bio`, ссылка на секцию — в `sourceUrl`, совпавшие
  владельцы — строками `MascotOwner`. Владельцы перепроверяются в
  момент одобрения серверным guard'ом «только SOLO/BAND» (как
  `getMascotOwnerData`). Маскота с таким именем успели завести руками —
  просто линкуем, дубль не создаётся. Ошибка показывается над очередью
  (`?mascotError=`).
- **«Отклонить»** — REJECTED через `ConfirmForm` (обход больше не
  предложит).
- **Массовых действий нет намеренно** — маскотов единицы, а каждое
  одобрение — новая карточка каталога.

**Бейджи**: PENDING-черновики — на вкладке «Маскоты» и четвёртой
составляющей в счётчике `/admin/imports` сайдбара (`adminBadgeCounts`).
