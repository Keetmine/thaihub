# Краулер афиши ThaiTicketMajor (черновики событий)

Суточная задача `ttm-crawl` обходит две категории афиши
thaiticketmajor.com — [/concert/](https://www.thaiticketmajor.com/concert/?lang=en)
и [/performance/](https://www.thaiticketmajor.com/performance/?lang=en) —
и ищет в составе каждого события артистов из нашего каталога. Совпало —
событие становится **черновиком** в очереди на проверку; владелец
заходит и одобряет или отклоняет каждый. Само в афишу не попадает
ничего.

## Files

- **`src/lib/ttmCrawl.ts`** — сам краулер (`runTtmCrawl` +
  `summarizeTtmCrawl`): листинги → новые URL → страницы событий →
  матчинг → `EventDraft`.
- **`src/lib/thaiticketmajor.ts`** — парсер списочных страниц
  (`parseTtmListing`/`scrapeTtmListing`, карточка `.event-item a.title`)
  и канонизация адреса события (`canonicalTtmEventUrl`) — рядом с
  существующим парсером страницы события `scrapeTtmEvent`. Тот же UA,
  кука `__la=en` и 15-секундный таймаут.
- **`src/lib/eventDedupe.ts`** — матчинг «спарсенное событие ↔ Event
  каталога» по названию и датам (см. «Дубли и бэкфилл источника» ниже);
  строковые функции чистые, БД — только в `findCatalogDuplicate`.
- **`scripts/dedupe-event-drafts.ts`** — разовая чистка уже созданной
  очереди тем же матчингом (черновой режим по умолчанию, `--apply`).
- **`src/lib/performerMatching.ts`** — матчинг состава с каталогом
  (`matchArtistsByNickname`), вынесен из «события по ссылке»
  (`events/importActions.ts`) и общий для обоих путей: точное
  case-insensitive совпадение ника с `Performer.name`, без фаззи —
  ложная привязка хуже пропуска.
- **`src/lib/scheduledJobs.ts`** — задача `ttm-crawl` в
  `JOB_DEFINITIONS` (`logKind: "ttm-crawl"`, `logsItems: true` — история
  прогонов и найденного видна на вкладке задачи в `/admin/schedule`).
- **`src/app/admin/(protected)/imports/`** — очередь на вкладке
  «События» (`page.tsx`), экшены «Одобрить»/«Отклонить»
  (`eventDraftActions.ts`), прокси постера (`ttm-poster/route.ts`).

## `EventDraft` — своя таблица, не флаг на `Event`

До одобрения краулер публичной таблицы `Event` **не касается вовсе**:
флаг «черновик» на `Event` заставил бы фильтровать каждую публичную
выборку, и одна пропущенная = утечка неподтверждённого события на
витрину.

Поля: `sourceUrl` (канонический адрес без utm, `@unique` — ключ
дедупа), `payload Json` (весь распарс `TtmEvent`: название, даты,
площадка, цена, постер-URL, пресейл, состав), `matchedPerformers Json`
(`[{performerId, nickname}]` — Json, а не join-таблица: нужны только
чипы в очереди и привязка при одобрении), `status`, `eventId?` (после
одобрения), `createdAt`/`checkedAt`/`reviewedAt`.

`EventDraftStatus`:

- **PENDING** — ждёт решения владельца (очередь, бейджи);
- **APPROVED** — событие в каталоге, `eventId` указывает на него: либо
  владелец одобрил (событие создано), либо краулер/скрипт чистки сам
  закрыл черновик как **сильный дубль** уже существующего события (см.
  «Дубли и бэкфилл источника») — семантика та же, что у «Одобрить» при
  уже существующем `sourceUrl`;
- **REJECTED** — вечная память: повторный обход решение не воскрешает;
- **NO_MATCH** — совпадений не было; тоже память (не перекачиваем), но
  с **re-check**: когда `checkedAt` старше 7 дней, страница
  перечитывается — артисты появляются в каталоге позже, чем событие в
  афише, и вчерашний NO_MATCH завтра может совпасть.

Таблица заодно и память краулера: URL, уже существующий как
`Event.sourceUrl` (включая события, заведённые руками через «событие по
ссылке»), — пропуск навсегда. Чистка `cleanup-expired` черновики **не
трогает** — REJECTED/NO_MATCH и есть память, её нельзя ротировать.

## Прогон задачи

1. Обе списочные страницы — по одному запросу за прогон, не чаще.
   Упавшая категория не отменяет вторую; упали обе — прогон падает
   честно. В карточках отсеиваются внешние сайты (Ticketmaster), чужие
   категории (/sport/ из блока RECOMMENDED) и дубли.
2. По каждому новому/перепроверяемому URL — страница события
   существующим `scrapeTtmEvent`, с паузой 1.7 с между страницами.
   Потолок — **40 страниц событий за прогон** (свежих карточек в двух
   категориях ~70, при первом прогоне хвост добирается назавтра).
   Новые URL идут раньше re-check'ов.
3. Дедуп по содержимому (`findCatalogDuplicate`, см. «Дубли и бэкфилл
   источника»): сильное совпадение с каталогом — черновик не создаётся,
   `sourceUrl` бэкфилится; слабое — черновик получит пометку
   `possibleDuplicateOf`.
4. Матчинг `matchArtistsByNickname`; ≥1 совпадения → PENDING (с
   `ImportedItem` типа `event-draft` в журнал), 0 → NO_MATCH. Ошибка
   одной страницы прогона не роняет.
5. Появились новые PENDING → **одно** `notifyAdmins("import",
   "Черновики событий: +N, ждут проверки")` с dedupKey прогона — не по
   сообщению на черновик.

Прогон пишется через `logImportRun` (kind `ttm-crawl`, есть
«Остановить»), сводка — `summarizeTtmCrawl` (карточек / скачано /
черновиков + ники / без совпадений / пропущено).

Akamai у TTM пропускает Node-fetch, но режет curl (TLS-отпечаток) — не
пугаться 403 при отладке из шелла.

## Дубли и бэкфилл источника

Дедуп только по `Event.sourceUrl` слеп к событиям, импортированным
**до** того, как ссылка-источник начала сохраняться (roadmap Э1.8): их
`sourceUrl` пуст, по URL они «новые», и первый живой прогон предложил
владельцу черновики того, что в каталоге уже есть. Поэтому перед
созданием черновика каждый распарс прогоняется через
`findCatalogDuplicate` (`src/lib/eventDedupe.ts`) — матчинг по
названию и датам.

**Нормализация названия** (`normalizeEventTitle`): HTML-мнемоники
(`&#39;` из JSON-LD) раскодируются, casefold + NFKC, пунктуация,
кавычки и тире схлопываются в пробелы. Слова **не выкидываются**:
«X CONCERT» и «X FAN MEETING» — разные события одного артиста.

**Похожесть** (`titleSimilarity`, 0..1, без внешних либ): единица минус
расстояние Левенштейна / длину длинного названия; плюс
префикс-надбавка `0.6 + 0.4·(короткое/длинное)`, когда короткое
название целиком стоит в начале длинного по границе слова (типичные
хвосты TTM: спонсор, год, «IN BANGKOK») — надбавка требует от общего
куска ≥2 слов и ≥10 символов, одно имя артиста её не получает.

**Уровни** (пороги `STRONG_TITLE_SIMILARITY = 0.82`,
`WEAK_TITLE_SIMILARITY = 0.55`):

- **сильное** — нормализованные названия равны, ЛИБО похожесть ≥ 0.82 и
  есть хотя бы одна общая дата occurrence'а. Исключение: равные
  названия при заведомо разных датах обеих сторон — лишь слабое
  (ежегодное событие с тем же названием: иначе URL новой афиши навсегда
  пришился бы к прошлогоднему событию);
- **слабое** — похожесть ≥ 0.82 без общих дат, или общая дата при
  похожести ≥ 0.55.

**Что делает краулер.** Сильное: черновик не создаётся; на совпавший
`Event` бэкфилится `sourceUrl` (если пуст) — быстрый путь по URL дальше
работает сам; URL запоминается черновиком **APPROVED** с `eventId`
(без нового значения enum; краулер APPROVED не перекачивает). Слабое:
черновик создаётся как обычно, но в payload дописывается
`possibleDuplicateOf: {eventId, eventTitle}` — название лежит в самой
пометке, чтобы карточка рисовалась без лишнего запроса и не боялась
удалённого события. В сводке прогона — «дублей закрыто N, возможных
дублей M».

**Кандидаты ищутся недорого**, не полным сканом: события с
occurrence'ами в окне дат черновика ±14 дней плюс события с самыми
длинными «содержательными» токенами названия подстрокой
(частые слова афиши — concert, bangkok, tour… — в поиск кандидатов не
идут, но в самом матчинге участвуют); потолок выборки 300.

**Разовая чистка очереди** — `scripts/dedupe-event-drafts.ts`: тот же
матчинг по всем PENDING-черновикам. Сильное → черновик APPROVED c
`eventId` + бэкфилл `sourceUrl`; слабое → пометка `possibleDuplicateOf`.
По умолчанию черновой режим (печатает: черновик → с кем совпал → что
сделает), применение — `--apply`:

```
npx tsx --env-file=.env scripts/dedupe-event-drafts.ts          # показать
npx tsx --env-file=.env scripts/dedupe-event-drafts.ts --apply  # применить
```

## Очередь в админке

`/admin/imports?tab=events`, блок «Черновики событий (N)». Карточка:
постер-превью, название ссылкой на TTM, даты/время/площадка, чипы
совпавших артистов (ссылки на их админ-карточки).

- **«Одобрить»** — создаёт событие **существующим путём**
  `createEventFromTtmImport` (одна транзакция, постер скачивается к нам
  через `downloadRemoteImage`, мультидень из `extraDates`, пресейл);
  черновик → APPROVED + `eventId`. К событию привязываются **только
  совпавшие** артисты (`extraPerformerIds`): остальной состав спарсен
  эвристикой `parseArtistLine`, и новых исполнителей без ручной
  проверки не заводим — добираются в карточке события. Если событие с
  этим `sourceUrl` уже есть — просто линкуем, дубль не создаётся.
  Ошибка создания (на странице не было даты и т.п.) показывается над
  очередью (`?draftError=`), такое событие заводится руками через
  «событие по ссылке».
- **«Отклонить»** — REJECTED через `ConfirmForm` (действие
  необратимо для краулера).
- **Чип «Возможный дубль: <название>»** (`.event-chip-warning`, рядом с
  кнопками) — у черновиков с пометкой `possibleDuplicateOf` в payload
  (слабое совпадение матчинга дублей); ведёт на админ-карточку нашего
  события, чтобы сравнить и отклонить в один взгляд.
- Массовых действий **нет намеренно**: владелец хочет смотреть каждый.

**Постер-превью — через прокси** `/admin/imports/ttm-poster?draft=<id>`
(гейт `isCatalogEditor`, наружу URL не принимается — берётся из payload
черновика и проверяется на хост TTM): прямой `<img>` на
`img_poster/…` браузер не грузит — Akamai режет кросс-сайтовые
картинки (`Sec-Fetch-Site` → 403 → `ERR_BLOCKED_BY_ORB`), а серверный
fetch проходит. В базу чужой хост по-прежнему не пишется — скачивание
только при одобрении.

**Бейджи**: PENDING-черновики входят в счётчик `/admin/imports` сайдбара
(`adminBadgeCounts`, вместе с упавшими запусками и MDL-заявками) и в
бейдж вкладки «События».
