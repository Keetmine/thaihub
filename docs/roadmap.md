## Почта (отложено 2026-08-18, решение за владельцем)

- [ ] Выбрать и подключить почтовый сервис. Ограничение: аудитория в
      РФ, Cloudflare-решения не подходят. Исследовано:
      бесплатных ящиков на домене с SMTP не осталось — Яндекс 360 и
      VK WorkSpace платные (~250–310 ₽/юзер/мес), у Zoho бесплатный
      тариф только webmail (без SMTP/IMAP). Бесплатное комбо: Zoho
      Free (ящик admin@, читать через веб) + Unisender Go (SMTP,
      1500 писем/мес бесплатно, российский). Проще всего — платный
      Яндекс 360: один сервис закрывает и ящик, и SMTP
      (smtp.yandex.ru:465, пароль приложения). Шаги — в docs/deploy.md.
      Код готов весь: SMTP_* в .env + admin_notify_email в настройках.
- [ ] Пока почты нет: сброс пароля недоступен (вход через
      Google/Telegram работает), ответы на обращения — с личного ящика
      через mailto, админ-уведомления — только Telegram.

## Ю. Аудит 2026-08-30: безопасность, производительность, SEO

### Ю1. Безопасность

- [x] Ю1.1 (КРИТИЧНО). `createOwnLocation` экспортировался из
      `"use server"`-модуля и брал `userId` аргументом — Next присваивает
      такому экспорту action-id, то есть функция вызывалась прямым POST
      без входа: создание места от чужого имени, слепой SSRF и запуск
      Chromium (~250 МБ) на каждый вызов. Вынесена в обычный модуль
      `src/lib/ownLocation.ts`. Проверены ВСЕ `"use server"`-модули —
      других экспортов, принимающих userId/права аргументом, нет.
- [x] Ю1.2. Rate-limit обходился подделкой `X-Forwarded-For`: брался
      первый элемент, а Caddy дописывает реальный IP в конец. Теперь
      последний. Обход `E2E_RATE_LIMIT_OFF=1` — только вне production.
- [x] Ю1.3. Security-заголовки (их не было вовсе): HSTS, nosniff,
      X-Frame-Options, Referrer-Policy, Permissions-Policy в
      `next.config.ts` + nosniff для `/uploads/*` в Caddy (идут мимо
      Next). Боевой CSP НЕ вводили — сломал бы Метрику/GTM/Sentry;
      добавлен Report-Only, enforcing — отдельная задача.
- [x] Ю1.4. Хранимый XSS в вики: контент рендерился сырым HTML без
      санитизации. `sanitize-html` на сохранении И на рендере — второй
      пояс делает безопасными старые статьи без миграции.
- [x] Ю1.5. SSRF: `src/lib/urlGuard.ts` — запрет loopback/RFC1918/
      link-local (метаданные облаков)/CGNAT/IPv6-вариантов, ручное
      следование редиректам с ре-валидацией каждого хопа; для
      пользовательских maps-ссылок сверху allowlist Google-хостов.
- [x] Ю1.6. Path traversal в имени скачиваемой картинки
      (`%2e%2e%2f` переживал decode после split) — basename + проверка,
      что путь не вышел из `public/uploads`.
- [x] Ю1.7. «Усыновление» чужого приватного файла: `/files` авторизует

- [x] Ю1.8. Прочее: приглашения в поездку только друзьям; чужие

      **Условия возврата платного:** появился рабочий способ оплаты
      (см. ВВ2 про Boosty). **Перед выключением** — разослать
      предупреждение: в `/terms` обещано сообщить о завершении акции
      заранее, инструмент есть (`/admin/broadcast`). Подробности —
      docs/features/premium.md, раздел про промо-период.

## ВВ2. Оплата подписки через Boosty (исследовано 2026-09-15, не делаем)

Владелец завела Boosty и уровень подписки; там же можно принимать
разовые донаты. Вопрос был: можно ли встроить это в сайт так, чтобы
человек оплатил и подписка включилась сама. **Можно — но не через API,
а через Telegram.** Ниже — что выяснено и какую схему делать, когда
дойдут руки.

### Что Boosty умеет и чего не умеет

- **Официального API и вебхуков для авторов у Boosty нет.** Есть
  приватный API (`api.boosty.to/v1/blog/<blog>/subscribers`,
  `.../subscription_level`), которым живут неофициальные библиотеки:
  токен вынимается из cookies браузерной сессии автора и протухает.
  Список подписчиков он отдаёт с email и уровнем. **Как основу брать
  нельзя**: сломается без предупреждения, а email на Boosty и у нас —
  разные у половины людей.
- **Зато есть штатный бот `@boosty_to_bot`.** Он пускает подписчиков
  нужного уровня в закрытую Telegram-ГРУППУ и сам выкидывает тех, у
  кого подписка кончилась. Требует: привязанный Telegram у автора и у
  подписчика, бот — админ группы с правами бана и создания
  инвайт-ссылок. **С каналами не работает, только с группами.**
- **Комиссия** — 11,7% с платежа (вместе с эквайрингом) плюс комиссия
  за вывод.
- **Вывод нерезиденту РФ** — только «банковская карта» в USD или EUR.
  Для белорусской карты это единственный путь.
- **Оплата** — карты (RUB/USD/EUR), ЮMoney только для резидентов РФ.
  Иностранные карты Boosty принимает, но у плательщиков из РБ бывают
  отказы.
- **Patreon отпадает**: API и вебхуки у него отличные, но выплаты
  только PayPal/Payoneer (в РБ нет), а российские карты подписчиков
  там не проходят.

### Схема, которую делать

Ничего приватного, никаких токенов из cookies — только то, что Boosty
поддерживает штатно:

1. Закрытая группа «Подписчики MyBLHub». В ней админами `@boosty_to_bot`
   и наш бот.
2. Человек платит на Boosty → привязывает там Telegram → бот Boosty
   зовёт его в группу.
3. **Наш бот ловит вход в группу** (`chat_member` / `new_chat_members` в
   вебхуке), находит `User` по `telegramId` и продлевает `premiumUntil`.
4. **Ночная сверка**: кто ещё в группе — продлевается, кого Boosty
   выкинул — не продлевается. Само истечение отрабатывает уже
   существующий `premiumUntil`, отдельного механизма снятия не нужно.
5. На пейволле вместо «написать нам» — кнопка «Оформить на Boosty» и
   три шага. Запасной путь для тех, у кого нет Telegram, остаётся
   прежний: одноразовый промокод из админки.

Ограничение схемы: человек должен привязать Telegram и на Boosty, и у
нас. Для нашей аудитории это приемлемо.

### Что проверить ДО того, как писать код

Оба пункта практические, кодом не проверяются:

- проходит ли **вывод** Boosty на карту владельца (валютный счёт
  USD/EUR) — пробным маленьким выводом;
- проходит ли **оплата** с белорусской карты у подписчика.

### Налоги и анонимность

Деньги с Boosty, скорее всего, **не «подарок»**: платит не человек, а
Boosty как российское юрлицо по договору с автором — для НПД это доход
от иностранной организации, а не дарение между физлицами. Владелец
намерена платить налог в любом случае, так что вопрос снимается
внесением выплат в приложение НПД по факту поступления. **Уточнить у
налоговой.**

С анонимностью конфликта нет: налоги не всплывают на сайте. Но блог на
Boosty стоит **переименовать в MyBLHub** и сменить адрес с личного ника
— для подписчика продавец Boosty, автор бренд, владельца как личности
нигде нет. В документах сайта оплата описывается как «через Boosty»,
без реквизитов.

## ГГ. Хотелки владельца 2026-09-23

- [ ] ГГ1. **Честная сортировка по оценке MyDramaList** (вопрос
      владельца 2026-09-23: «появилось много сериалов с оценкой 10, но
      там только одна оценка — насколько честно такое выводить?»).
      Сейчас `?sort=mdlScore` сортирует сырой оценкой, и наверху
      каталога стоят 17 записей с 9.5+, у которых **ни одной** нашей
      отметки просмотра, — десятка от одного голоса весит столько же,
      сколько 8.7 от тысячи. Не враньё, но подпись «по оценке» читается
      как «лучшее», и это обещание не выполняется.
      Чинится числом голосов: завести `Drama.mdlVotes`, тянуть его тем
      же проходом `mdl-sync-dramas` (в JSON-LD MDL рядом с
      `ratingValue` обычно лежит `ratingCount`, запасной вариант —
      строка «from N users» на странице), сортировать взвешенной
      оценкой по формуле IMDb `(v/(v+m))·R + (m/(v+m))·C` (m ≈ 50
      голосов, C — средняя по каталогу), считая её при синке в
      отдельную колонку под индекс. Ничего не прячем: одинокая десятка
      просто съезжает к середине. В карточке рядом с оценкой печатать
      число голосов — тогда и она выглядит честно.
      **Сначала проверить**, что `ratingCount` на странице есть: с
      машины разработки MDL отвечает Cloudflare-проверкой, нужен один
      заход с машины, которую MDL пропускает.

## Сильно на будущее: видео-сайт-спутник и публичный API (обсуждено 2026-08-28)

Идея владельца: отдельный сайт с видео серий на своём домене и своём
сервере, «одноразовый» — при блокировке быстро поднимается зеркало на
новом домене. Ожидаются блокировки на территории РБ/РФ (ЛГБТ-контент).
Решение из обсуждения — не общая база и не синхронизация двух баз, а
API основного сайта; вернуться, когда владелец решит делать.

Принцип одноразовости: видео-сайт не хранит ничего невосполнимого.
- Пользовательские данные — ТОЛЬКО у нас: видео-сайт ходит
  сервер-к-серверу с сервисным токеном (свой на каждое зеркало,
  отзываемый) — «сериалы юзера» забирает, «просмотрено» пишет в наш
  DramaWatchStatus. Источник правды один, синхронизировать нечего.
- Видео-файлы — в отдельном хранилище, не на сервере сайта: зеркало —
  это тонкий фронт (новый домен + сервер, тот же сторадж и API).
- Браузеры пользователей НЕ ходят на наш домен напрямую (кроме
  момента входа): все запросы видео-сайт проксирует своим бэкендом —
  переживает блокировку любого из двух доменов.
- Вход «через MyBLHub»: редирект к нам, одноразовый код, обмен на
  сессию видео-сайта (упрощённый OAuth на нашей UserSession).
- У нас настройками (не кодом): список разрешённых доменов-зеркал +
  адрес текущего зеркала для ссылки на сайте — смена домена без
  деплоя.
- Разные серверы и РАЗНЫЕ IP обязательно: блокировки бывают по IP,
  общий адрес утянет оба сайта.

Проговорённые риски (решение владельца делать — принято осознанно):
API-скрытность не даёт юридической развязки — сайты связывает общий
владелец (домены, оплата, хостинг), а не API; видимые связи — вход
через нас, общие счётчики и сама ссылка с главной (к ссылкам на
заблокированное в РФ тоже бывают претензии — риск именно для
основного сайта). Права на видео — отдельный вопрос; легальная
альтернатива на часть каталога — официальные YouTube-эмбеды (выше).
Самая тяжёлая часть проекта — не связка, а раздача видео: место,
трафик, HLS, CDN, работающий из РФ без Cloudflare.
